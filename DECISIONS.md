### D14 — Local MCP servers are project-scoped and committed *(2026-08-06)*
Five stdio servers (`chrome-devtools`, `context7`, `sequential-thinking`,

**Why:** the toolchain is part of the project, reviewable in git, and identical
for anyone who clones it. User-scope config is invisible to review and drifts
per machine. Project scope costs one approval prompt per user, which is the
correct security posture for executable config.

Each was verified with a real `initialize` + `tools/list` handshake before
being recorded as installed. `@modelcontextprotocol/server-github` was
**rejected** — npm marks it `Package no longer supported`; the remote server at
`api.githubcopilot.com/mcp/` replaces it.

### D15 — Third-party component registries are declined *(2026-08-06)*
21st.dev, Magic UI, Aceternity, Origin UI, React Bits, Motion Primitives and
HyperUI are **not installed**, despite being available.

**Why:** `brand-os/03_component-language` already defines this project's
component language, implemented against its design tokens. Importing components
built on someone else's tokens forks the design system — precisely the drift
DEC-302 exists to prevent. The constraint here is governance, not capability.

**What would change this:** a genuinely new interaction surface with no
in-house precedent (a command palette, a combobox). Even then, prefer **Radix
primitives** — unstyled behaviour only, no visual opinion, so tokens still
govern appearance.

### D16 — Source maps ship off, and are enabled only for profiling *(2026-08-06)*
`productionBrowserSourceMaps` is gated on `PROFILE_SOURCEMAPS`; `npm run
build:profile` sets it.

**Why this is safe to compare against production:** enabling maps appends a
`sourceMappingURL` comment and writes sibling `.map` files. The JS is otherwise
byte-identical, and browsers never fetch maps unless devtools is open. A
profiling build therefore measures the code production ships.

### D18 — The entity graph is emitted per route, not from the layout *(2026-08-07)*
`lib/structured-data.ts` builds one `@graph` per page; `layout.tsx` emits none.

**Why:** the graph lived in the root layout, which was correct while the site
was one route and became wrong the instant it was not. Every sub-page would
have inherited `@id: <site>/#webpage` — asserting that it *is* the homepage —
plus the homepage's `FAQPage`. That is not a cosmetic error: it tells a
consumer two URLs are the same entity.

**What was preserved:** the "exactly one JSON-LD block per page" rule, and its
reasoning — one linked graph resolves in a single pass, four loose blocks make
a consumer guess how they relate. `seo.spec.ts` asserts it on every route now
rather than only on `/`.

`Organization` and `WebSite` repeat on every page. That is how schema.org
graphs are meant to work: each page is independently resolvable, and identical
`@id`s let a consumer merge them.

### D19 — `BreadcrumbList` ships, and still not on the homepage *(2026-08-07)*
Emitted on `/services` and the four service pages. **Not** on `/`.

**Why the reversal is not a reversal:** the prior decision was that a breadcrumb
for a page with no ancestors is schema spam. That reasoning was never about
breadcrumbs being bad — it was about the site having no hierarchy. The service
tree created one, so `Home › Services › WhatsApp Automation` names three pages
that all exist and all return 200. The homepage still has no ancestors and still
gets none, asserted by a test so "add breadcrumbs everywhere" cannot land
without confronting this entry.

`/services` exists partly to make the middle crumb real. A trail with a hole in
it is worse than no trail.

### D20 — Service-page claims are gated by test, not review *(2026-08-07)*
Two assertions in `seo.spec.ts`: every service page's `name`/`serviceType` must
match its `Offer` in the catalogue, and every integration it names must already
appear in the published integrations answer in `content/faq.ts`.

**Why type-level enforcement was not enough here.** D1 put fabricated *customer
proof* beyond expression in the type system. These pages create a different
hole: prose. A new tool name or a reworded service is valid TypeScript, reads as
a copy edit in review, and quietly becomes a capability claim — on the pages
*most* likely to be quoted verbatim, because each is narrowly on-topic. The test
is the cheapest thing that fails when it happens.

### D22 — The boot sequence runs on the homepage only *(2026-08-07)*
`LoadingScreen` lived in the root layout, so once the site gained routes it
played its ~1,850 ms full-screen overlay on every one of them. It is now gated
to `/`.

**Measured, same route, same instrument, median of 5, mobile:** Speed Index
**4.9 s → 3.3 s**. LCP did not move (4.4 → 4.5 s) and the score change (59 → 60)
is inside this machine's spread. So the honest claim is narrow: the overlay was
delaying *visual progress*, not the largest paint.

**The experience argument is the stronger one and needs no metric.** A service
page is a search landing surface. Someone arriving from a query for "whatsapp
automation" should not watch a brand boot animation before reading the answer
they clicked for. The sequence is untouched where it was designed to live — the
homepage, first impression.

**This touches the brand experience, so flag it for review.** It is reversible
in one line (drop the `isHome` guard), which also reverts the Speed Index
result. If `LOADING_PHILOSOPHY` intends the boot on every surface, say so and it
comes back.

### D23 — Mobile and desktop are different problems *(2026-08-07)*
Not a choice so much as a finding that constrains future work, recorded so it is
not re-derived.

**Desktop is paint-bound** — 73–91% of main-thread time, and the homepage's
specific decorative composition (see A2).

**Mobile is bandwidth-bound.** The mobile preset simulates Slow 4G at 1.6 Mbps;
~340 kB gzipped JS plus 228 kB of preloaded fonts is ≈2.9 s of transfer before
anything paints. LCP measured 4.3–4.5 s on three routes whose payloads differ by
an order of magnitude — a metric that will not move with content is not
measuring content.

**Consequence: the desktop conclusion does not transfer.** Resolving A2 in
favour of a lighter composition would help desktop and do comparatively little
for mobile, where the lever is bytes — typefaces, subsets, unused JavaScript.
Do not treat one number as a proxy for the other.

### D17 — RESOLVED, in the negative *(opened 2026-08-06, closed 2026-08-07)*

**There is no single expensive effect.** The question assumed one existed; the
measurement says otherwise.

Steady state, 4 s idle, atmosphere confirmed mounted, CDP counters, median of 7–9:

| Arm | Total main-thread task |
|---|---|
| Motion on | 374 ms |
| Reduced motion (no atmosphere) | 246 ms |

Every isolating arm measured **higher** than baseline — `no-ambient-anim` +10%,
`no-breathe` +11%, `breathe-on-children` +17%, `no-particles` +24% — which is
impossible if any were removing real work. `no-blend`, `no-sheen` and
`no-backdrop-blur` were equally unseparable. **The blend-mode hypothesis is
unsupported.**

**Two retractions.** The original D17 entry recorded "~63% of TBT and 100% of
steady-state blocking". A later pass recorded "the breathing animation is 64% of
the cost". **Both were instrument artifacts:**

1. A **mount race** — `DeferredAtmosphere` mounts via
   `requestIdleCallback(..., {timeout: 3000})` and both profilers used a
   hard-coded 3,000 ms phase boundary, so the measurement window opened exactly
   when the subject appeared. The metric was bimodal (~370 / ~1,300 ms) and the
   same arm scored −64% and −2% on identical code.
2. **Observer effect** — 100 µs sampling inflated steady-state blocking from
   555 ms to 1,182 ms. Default is now 1,000 µs.

**What stands:** paint and compositing are 73–91% of steady-state and 76% of
load-phase main-thread time. JavaScript is the minority cost. The atmosphere
costs ~128 ms per 4 s (~9% duty cycle), and the page spends 246 ms per 4 s with
no atmosphere at all, 91% of it paint.

**Consequence:** the cost is diffuse and structural — a dark page with several
large translucent gradient layers is expensive to composite whether or not it
animates. There is no bug to fix. Reducing it means fewer or smaller translucent
layers, which is **A2**, a design decision.

### A2 — Does the cinematic identity survive its measured cost? *(now answerable)*
**D17 closed the way that makes this a design question.** The cost is not one
fixable effect; it is inherent to the composition — several large translucent
gradient layers over a dark page, expensive to composite animated or not.

**The honest scale, so this is decided on facts rather than dread:** the
atmosphere costs ~128 ms of main-thread time per 4 s (374 vs 246), about a 9%
duty cycle. Real, but far smaller than the ~40% an earlier retracted
measurement implied. Load-phase blocking is the larger gap — 488 ms with the
atmosphere against 124 ms without — though that compares *having* it to *never
creating* it, not animating it to freezing it.

**The lever, if one is wanted:** fewer or smaller translucent layers, or
cheaper fills. Not "turn off the animations" — the arms show that buys nothing
measurable.

**Recommendation: do nothing yet.** A 9% steady-state duty cycle does not
justify weakening the site's visual signature, and load-phase blocking is
better attacked through hydration cost (`next` 138 ms, `framer-motion` 90 ms),
which carries no design consequence at all. Revisit if mobile *field* data —
not lab numbers — shows INP suffering.
